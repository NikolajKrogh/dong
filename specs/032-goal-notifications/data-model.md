# Data Model: Active Game Goal Notifications

All new relations live in `private`, deny public, anon, and authenticated grants, and use explicit least-privilege server access. Apply RLS as defense in depth. Keep credentials out of responses, logs and analytics. Privileged functions use a fixed empty search path and named relations. Use the existing identity tables for ownership and lifecycle checks.

| Entity | Fields and constraints |
| --- | --- |
| Browser subscription | UUID, unique canonical endpoint hash, protected endpoint and P-256/auth keys, VAPID key ID, installation control credential digest, consent state, generation, created/updated/revoked timestamps. A registration retry with the same credentials is idempotent. Endpoint or UUID alone grants no authority. Prove possession through a high-entropy server-issued installation credential. Keep installation consent and the control generation separate from endpoint data so an expired endpoint can be purged while same-identity consent remains available for repair. A new identity requires explicit consent and its own authorized association. |
| Game association | One active binding per subscription. Bind to either room/session and participant with verified account or guest grant epoch, or finalized solo tracking grant ID. Store acknowledged version, bound time, expiry and revocation state. For guests and unsigned solo, record acknowledged common-match preference. For solo, a supplied common-match ID must be in the admitted selection. Signed-in preference uses existing account settings. Never store raw room guest or solo tokens. |
| Multiplayer scope | Keyed by room session and participant. Choices `assigned_and_common` and `all_room_matches`, with B as the implicit default. Version and acknowledged change boundary. Same participant in the same session sees the same choice on authorized browsers. Reject changes to another participant and reset for a new session. |
| Match eligibility boundary | Keyed by association and catalog match. Record membership identity or source selection revision, effective time and baseline accepted observation version. A new association, scope expansion, re-enabled common match, reassignment or re-added match baselines prior accepted scores. Existing authorized matches can preserve the boundary where membership continuity is proven. |
| Delivery ledger | UUID and unique `(subscription_id, catalog_match_id, observation_version)` for goal work. Store association generation, compact score projection or stable source references, accepted/deadline timestamps, state, attempt count, due time, lease token/expiry and redacted outcome class. No catalog FK that pins history. Test sends use a separate request ID and bounded throttle. |
| Dispatch policy | Private controls for test and live delivery, enabled targets, policy generation and enrollment limits. Starts disabled. Installations record their environment and target. Recheck target policy, consent and current eligibility before delivery. |

## Eligibility and concurrency

- Registered participation requires a verified current account and active participant in an in-progress room. Guest participation requires a current unexpired guest grant and the same live participant. Host privileges never bypass ownership checks.
- Solo binds only to an already finalized, unexpired grant. Hash the canonical decoded capability bytes as in the existing tracking service. Compute match coverage from its admitted rows. An acknowledged empty selection, expiry or grant termination ends eligibility. A different active game replaces the association atomically.
- Capture current catalog versions in the notification transaction when enrollment or an in-game scope change is acknowledged. For gameplay changes, reconcile from committed room match and assignment rows, `assignment_reassigned` and `assignment_replaced` evidence, and solo selection version. Recheck membership evidence at handoff. Timestamps alone are transaction-start timestamps. Where continuity or the exact newly eligible boundary cannot be proven, baseline the current version and suppress uncertain earlier changes. An independent reconciliation can conservatively skip a goal concurrent with reassignment. Verify this boundary on fixtures and keep score write transactions independent.
- Compare-and-set writes prevent stale tabs from overwriting newer scope or association state. At final server authorization immediately before network handoff, recheck the current committed consent, identity, membership, active game, scope, common preference, source corrections, expiry and rollout policy. A stop or scope change committed before that decision prevents an ineligible send. A stop acknowledged after that decision can race with handoff.
- Consume each authenticated scheduler wake lease once before claiming deliveries. Only one claim lease can authorize a delivery attempt. Use token-guarded completion so an old attempt cannot update a newer claim. The outbound request happens after commit with a deadline shorter than the lease. Record ambiguous network outcomes separately. A retry keeps the same logical delivery ID and Topic/tag. Provider handoff and device presentation can differ even when the ledger has one delivery.

## Lifecycle and cleanup

- Track consent separately from endpoint status. Observed permission revocation or reset revokes enrollment and clears consent. Provider-confirmed expiry invalidates only the endpoint and stops sends until repair for the same authorized installation. Transient and sender configuration failures leave both intact. Repair or new enrollment fences older attempts and baselines the currently authorized matches.
- Association states `active → superseded / stopped / expired`. A room close, departure, invalid guest grant, sign-out or solo expiry suppresses newly queued sends. Attempt server revocation before clearing sign-out credentials when online. Allow local sign-out if revocation cannot be acknowledged. Persist one retry with the existing installation control credential and old generation, separately from account tokens. Until the stop is acknowledged, server eligibility follows its last committed state and applicable expiry. An old-generation retry cannot disable a newer enrollment.
- Delivery states `pending → leased → accepted / pending / failed / suppressed / expired`. Retry only while within its original five-minute deadline. A provider acceptance is a handoff result. It is never proof of display.
- Index active associations by room/participant and solo grant, observation lookup by eligible match/version, and due work and expiry by partial indexes on live states. Test the query plan before adding an index to existing catalog observations. Remove expired associations and detected revoked/invalid subscriptions within 24 hours, and diagnostics within seven days. Retain the dedupe record at least through the candidate retry window. Expiry cleanup is independent of game-history maintenance.
- Ship additive migrations, policies and pgTAP tests. Existing games and preference rows require no backfill. Roll back by disabling test/live delivery and the send schedule. Keep bounded database-only cleanup scheduled to expire pending work and enforce both retention limits without waking the sender.
