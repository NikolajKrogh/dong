# Contracts: Goal Notifications

## Browser and player operations

Plan one narrow `goal-notifications` Edge entry point with typed operations. Validate request shape and exact allowed origins. Use the existing authenticated bearer, guest grant or finalized solo grant as appropriate. A server-issued installation control credential allows revoke/status for that installation, with current game authority required for enrollment, binding, test and scope writes. Derive all recipients and room selections server-side.

| Operation | Input and effect |
| --- | --- |
| Register | User consent, browser-generated endpoint and encryption keys, idempotency ID and appropriate game identity proof. Recheck target policy and enrollment limits. An exact retry returns the same outcome and cannot transfer an endpoint to another identity. Return an opaque installation handle and control credential. Keep subscription material private. |
| Bind or refresh game | Installation control plus current identity, active game reference and expected association revision. Server resolves active participant or solo grant and baselines covered matches. Guest/unsigned solo preference is an explicit boolean. Solo common fixture must be among admitted matches. Response includes effective eligibility and revision. The browser calls this after registration during in-game opt-in. It reports enabled for the current game only after bind acknowledgment. |
| Change multiplayer scope | Active authorized participant, expected scope revision and `assigned_and_common` or `all_room_matches`. Response acknowledges the session-scoped setting and new revision. Repeating the same request is idempotent. A stale conflicting request must reload current state. |
| Enrollment status | Check target availability before rendering Enable notifications. Return the public application-server key for an available target so the enable tap can start browser opt-in immediately. For an existing installation, verify its environment, credential and generation. |
| Disable | Installation control credential plus the expected enrollment generation. Idempotently revoke that enrollment and association. A stale retry may acknowledge an already inactive generation and must leave newer enrollment untouched. The browser can persist and retry this stop without an account token. Acknowledgment prevents later final send authorization for the affected generation. A previously authorized attempt can still reach handoff. |
| Repair subscription | Installation control, expected enrollment generation, current authorized identity and replacement endpoint. Preserve consent only for the same installation while permission remains granted, DONG consent remains active and rollout approval is valid. Replace the invalid endpoint, fence old attempts and establish a fresh game baseline. A revoked or reset permission requires a new explicit opt-in. |
| Test | Installation and current identity. Subject to cooldown and feature policy. Sends one fixed harmless message to the requesting registered installation. Response distinguishes accepted-by-service, unavailable and failure. |
| Resolve tap | Opaque delivery ID and current game authority. Return the route for a currently authorized matching game. Return a generic ended/access-lost outcome otherwise. Never join or replace a game implicitly. |

Responses carry a stable error code such as `unauthorized`, `invalid_destination`, `not_eligible`, `stale_revision`, `rate_limited` or `unavailable`. Authorization failures reveal no protected game or subscription metadata. Permission state stays local and is reconciled when the page opens or regains focus. An active registration does not establish device readiness or a game binding. Before prompting for permission, show the applicable enrollment state from the environment and target policy. Disabled targets see an unavailable state. Ordinary iPhone tabs see Home Screen setup guidance. Attempt the browser unsubscribe when available. If the server stop fails, report pending and retry on launch, foreground return or reconnection while DONG is open. Keep the installation control credential and expected generation until acknowledgment, separately from account credentials.

## Sender boundary

- The dedicated dispatch function accepts only the server's authenticated scheduler wake with a valid short-lived work lease. Reject missing or invalid scheduler credentials and expired, mismatched or consumed wake leases before claiming deliveries or making outbound requests. Accept each wake lease once. Verify effective read access to `net.http_request_queue` before implementing dispatch. Use a wake credential scoped to this dispatcher and bound to the expiring lease. Reuse the existing scheduler pattern only if it meets that boundary. Otherwise sign the wake with a dedicated secret stored in Vault and Edge secrets, and put only the short-lived proof in the queue. Keep project-wide credentials and the signing secret out of queue headers, bodies and logs.
- Check delivery policy and generation before claim and at final send authorization. Read current consent and game eligibility at final authorization and release database locks before network handoff.
- Validate endpoint syntax, bounds and encryption-key shape at registration and dispatch. Allow only HTTPS on the default port, with no userinfo, fragments, IP hosts or redirects. Allow verified push-service hosts and path families for the release browsers. Expected families include FCM, Mozilla Autopush and Apple's vendor-documented subdomains under `push.apple.com`. Confirm host and path patterns from actual subscriptions before enabling sends for a browser. Samsung's guide establishes Web Push support. Treat its endpoint family as unverified until measured on an Android device in the HTTPS preview. Record the host and redacted path pattern only. Use a DNS label boundary for approved vendor subdomains.
- Use an encrypted, versioned payload with a stable logical delivery ID, short title/body, and opaque tap reference. Content contains only fixture, accepted score and known scoring team or a neutral score update. No join codes, tokens, arbitrary URLs or player drinking details.
- Reuse the same logical delivery ID and notification tag on retry, including after an uncertain handoff. For a goal delivery, use its UUID without hyphens as the 32-character lowercase hexadecimal Web Push Topic. The worker shows the visible notification promptly with that tag, even when DONG is open. A tap focuses an authorized matching game or opens a same-origin guarded route. The test payload does not navigate into a game. A worker update must tolerate the previous payload version across deploys. Verify both focusing an open iPhone Home Screen window and opening an in-scope route from a closed one. Resolve access through the same guarded route in either case.
- Compute remaining TTL at send time, rounding down with a transit/deadline margin. Skip the attempt if the remaining TTL rounds down to zero. Retry transient network, 5xx and 429 outcomes with bounded backoff and a usable Retry-After within the original deadline. Disable only provider-confirmed expired or invalid endpoints. For Apple, classify 410 as expired, 404 as an invalid path and 403 as an authentication error. Preserve enrollment on sender configuration failures. For Mozilla Autopush, treat 404 with errno 102 or documented 410 endpoint errors as permanent for that endpoint and retain same-identity consent for repair. Use the provider and documented reason together when deciding to retire an endpoint. Provider acceptance is the only successful handoff signal used for release telemetry.
- Reuse Apple VAPID JWTs by push-service origin and signing key. Refresh no more than once per hour during normal operation. Verify the sender's reuse across repeated sends and Edge worker restarts before enabling production Apple sends.
