# Research: Active Game Goal Notifications

## Consume committed score evidence

**Decision** — Run a notification consumer independently of provider ingestion and room replay. Read immutable `private.provider_match_observations` by match and version. Use the previous version as the baseline, including when it precedes the scan window. Initial, missing or incomparable baselines produce no alert. Derive candidates from increases in normal scores and exclude unchanged scores, shootouts, aggregate-only changes and downward corrections. Group multiple increases in one accepted observation into one alert. Use goal wording only when the new goal evidence can be linked unambiguously. Use a neutral score update otherwise.

**Rationale** — The catalog writes score evidence for solo and multiplayer together and uses monotonically increasing per-match observation versions. See `20261025191037_match_catalog_core.sql` and the acceptance path in `20261026164719_match_catalog_retention.sql`. Goal detail revisions can enrich or retract evidence but lack a direct observation foreign key. They must not create a second candidate. Suppress pending deliveries invalidated by authoritative retractions or score rollbacks. If newer evidence makes the queued claim uncertain, suppress it instead of inventing goal details.

**Alternatives considered** — A trigger/outbox in the provider transaction could turn a notification write failure into a lost score update. Room events alone miss solo and can duplicate a match across rooms. Client polling cannot power closed-tab delivery.

## Resolve eligibility from the active game

**Decision** — Reuse verified account and registered-participant checks, current guest grant resolution, and the finalized solo grant digest. Derive recipients and match coverage server-side. A matches the active room's provider-backed match pool, subject to existing common-match filtering. B uses the player's live assignments plus common match. Use one personal setting per participant and room. Rejoining the same active participation retains the setting, and a new session starts at B. For a signed-in user, read the existing synced common-match preference from `public.settings.settings_data`. Accept an explicit acknowledged preference for guests and unsigned solo play.

**Rationale** — `private.active_catalog_room_matches` in `20261025193835_match_catalog_consumers.sql` creates monitoring demand for the common match and active assignments. The wider room pool can include unassigned fixtures that only receive incidental observations from existing acquisition. The all-room setting includes such fixtures if DONG accepts fresh evidence, and does not promise coverage where the catalog receives none. Explain this limit in the in-game control. If the user later wants independent monitoring for every pool match, assess it separately against provider budgets. Scope changes and new associations establish a committed baseline and never enqueue prior goals.

**Alternatives considered** — Trusting client match arrays bypasses current permissions and room edits. Restricting A to the union of assignments would change the clarified every-room-match choice. Adding a polling subscription per browser would conflict with the feature's acquisition constraint.

## Bound independent scheduling and storage

**Decision** — Use a dedicated Supabase Cron tick every 10 seconds, disabled at install. An independent database function scans bounded eligible observations within five minutes, inserts deduplicated work, and wakes the Edge sender through pg_net only when work is due and a lease is available. Use fair keyset batches across recent candidates and bounded overlap so concurrent commits cannot be skipped by a global high-water mark. Claims use short leases and row locks. Consume each authenticated wake lease once. Release all database locks before outbound HTTP. Keep database-only expiry and retention maintenance active when the send tick is disabled. Before implementing dispatch, check effective read privileges on `net.http_request_queue`. Supabase documents that this queue holds decrypted request headers pending delivery. The isolated local stack check on 2026-11-06 found effective schema usage and queue SELECT for anon, authenticated and service_role. This checks database grants and does not establish hosted API exposure. Queue only a dispatcher-specific, expiring proof bound to the single-use lease. Sign with a dedicated Vault/Edge secret if the existing scheduler credential is broader. The proof authorizes only the pre-existing lease and cannot create another one. Keep the project secret and any signing key out of queued requests. [Supabase scheduling documentation](https://supabase.com/docs/guides/functions/schedule-functions).

**Rationale** — A 10-second tick leaves room for the 30-second acceptance-to-display target. Supabase documents second-based schedules and private Edge invocation from Cron. A 31-day month contains 267,840 ten-second ticks. A wake per tick would consume over half the Free Edge invocation allowance of 500,000 before any existing traffic. With wake-on-work, measure actual catalog traffic plus projected notification wakes and API calls. Rollout requires a configured cap within remaining allowance, a measured reserve for existing workloads, and no increase in ESPN requests. See [Cron quickstart](https://supabase.com/docs/guides/cron/quickstart), [Edge invocation pricing](https://supabase.com/docs/guides/functions/pricing), and [runtime limits](https://supabase.com/docs/guides/functions/limits).

**Capacity validation** — Start with at most 50 installations, 25 claims per tick and five network sends at a time. A 31-day projection is existing monthly invocations plus 2,678,400 divided by 10 times measured wake fraction, plus registration and test calls. Measure database growth as daily logical deliveries times measured row-plus-index bytes times seven days, plus bounded association and subscription rows. Profile scan/claim/revalidation and expiry indexes with fixture fan-out. Check p95 queue age and CPU before expansion, and expire excess work within its original deadline. The numbers are starting limits for a preview and do not represent measured production capacity. Record numerical p95 queue-age and worker CPU limits plus minimum invocation and database headroom before the first production cohort. Compare score acceptance, room processing and provider requests against a notification-disabled baseline. Pause sends on any safety or gameplay regression. Hold expansion if SC-001 or a capacity threshold fails. [Google SRE guidance on canary evaluation](https://sre.google/workbook/canarying-releases/).

**Alternatives considered** — The catalog worker's existing cadence and deadlines should not absorb push I/O. A scheduled unconditional Edge request spends quota while idle. Redis or an extra queue service adds infrastructure for work the existing database can bound.

## Use the browser's Web Push service

**Decision** — Use the standard VAPID and encrypted payload path. The test-alert milestone should validate pinned `npm:web-push@3.6.7` and its `generateRequestDetails` API in the pinned Deno typecheck, local Supabase Edge runtime and isolated HTTPS preview. Send with native Fetch under explicit destination, redirect and timeout checks. If the candidate fails, stop live enablement and select a reviewed compatible implementation. Keep one stable key pair per environment and store private material as an Edge secret. Pass a strictly positive remaining TTL or skip the send. Apple requires a positive TTL even though RFC 8030 defines zero. The pinned library calls the VAPID header generator per request. Verify reuse of Apple JWTs by push-service origin and signing key, with refresh no more than once per hour. Check repeated sends and an Edge worker restart. [Apple Web Push requirements](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) · [RFC 8030, section 5.2](https://www.rfc-editor.org/rfc/rfc8030.html#section-5.2) · [Pinned sender source](https://github.com/web-push-libs/web-push/blob/v3.6.7/src/web-push-lib.js).

**Rationale** — Using a reviewed sender library avoids implementing VAPID and payload encryption in DONG. Supabase documents npm imports. Library compatibility is still a runtime gate. The worker validates payload shape and immediately shows a visible notification in the push event. The same stable logical ID supplies the transport Topic and presentation tag to reduce duplicates. A tag replaces a prior presentation and cannot promise exactly-once receipt or sound. Use the delivery UUID without hyphens as the Topic to fit Mozilla's documented alphanumeric limit. Keep endpoint classification provider-specific. Mozilla documents 404 with errno 102 as an invalid endpoint. Apple documents 404 as an invalid request path. Samsung confirms Web Push support but its developer guide does not specify a stable endpoint family. Verify it on a real enrollment before allowing sends. [Mozilla Autopush errors](https://mozilla-services.github.io/autopush-rs/errors.html) · [Apple Web Push](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) · [Samsung Internet developer guide](https://developer.samsung.com/browser/android/web-developer-guide.html).

**Alternatives considered** — Expo native push does not provide the browser path. A declarative Apple-specific path adds a second format before the shared path is verified. Sender helpers that own outbound HTTP complicate destination and redirect control.

**References** — [Supabase dependencies](https://supabase.com/docs/guides/functions/dependencies), [web-push API](https://github.com/web-push-libs/web-push#generaterequestdetails), [RFC 8030](https://www.rfc-editor.org/rfc/rfc8030.html), [Apple Web Push guidance](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [Supabase changelog](https://supabase.com/changelog). Keep the repository's CLI version during this feature and use explicit local validation. The November 4 CLI v3 change is outside this plan.

## Recover consent and pending stops in the foreground

The one-off Background Sync API is unavailable on Firefox for Android and iOS Safari. Supabase local sign-out can clear the browser session before server revocation is acknowledged, and an existing access token can remain valid until expiry. Persist the pending stop by installation and generation. Retry on launch, foreground return or reconnection while DONG is open. Treat a subscription-change event as an optional signal. On launch or foreground return, compare browser permission, the current endpoint and DONG consent. Repair an expired endpoint only while permission and same-identity consent still hold. [MDN compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/SyncManager.json) · [Supabase sign-out](https://supabase.com/docs/reference/javascript/auth-signout) · [W3C Push API](https://www.w3.org/TR/push-api/#security-and-privacy-considerations).

## Keep enrollment and notification taps small

**Decision** — Add the manifest through the single-output HTML template, serve a small push-only worker from the same origin, and use an opaque delivery reference for taps. Reuse authorized game routing after resolving current access. Use explicit installation guidance on iPhone. An installed website can require sign-in or room rejoin because browser storage is separate. Preserve the original tab's data and explain that a local-only game does not transfer automatically.

**Rationale** — The project exports a single SPA to Cloudflare Pages. Static assets must resolve as JavaScript/manifest rather than its HTML fallback. Validate Android in the isolated HTTPS preview. Collect Home Screen delivery feedback from iPhone users after production enablement. Desktop tests cover contracts and guidance. Expo documents `public/index.html` for single output. Cloudflare Pages can serve the SPA HTML for a missing asset, so inspect the worker's content type and body in the deployed preview. A WebKit report describes older iOS builds opening the Home Screen start page on a cold notification tap. A later retest could not reproduce it. Collect observations of both open and closed tap paths from production users. [Expo PWA guide](https://docs.expo.dev/guides/progressive-web-apps/) · [Cloudflare Pages route matching](https://developers.cloudflare.com/pages/configuration/serving-pages/) · [WebKit issue and retest](https://bugs.webkit.org/show_bug.cgi?id=263687).

**Alternatives considered** — An offline cache brings stale bundle risk without helping this feature. Notification payloads containing room codes or tokens would expose them on devices and in URLs. A custom solo transfer is outside this plan.
