# Implementation Plan: Responsive Match Discovery with Reusable Results

**Branch**: `codex/cache-match-discovery` | **Date**: 2026-10-30 | **Spec**: [spec.md](spec.md)

**Input**: `specs/031-cache-match-discovery/spec.md`

## Summary

Make selected league codes and the selected discovery date drive demand. Reuse the existing TanStack Query client for one public, session-only entry per league/date, and add a small batch loader that combines same-date misses into existing discovery requests. Publish each returned league immediately; keep usable fixtures visible through another league's pending checks or a refresh failure.

The picker will request one snapshot at a time through the existing football-match service. Its shared query state owns the initial check plus at most two pending follow-ups. Preserve the service's current default follow-up behavior for legacy live-score identity recovery. No database migration, backfill, backend deployment, new cache library, Redis, or provider-policy change is required.

## Technical Context

**Language/Version**: TypeScript 5.9; React 19.2.3; React Native 0.86.3; Expo SDK 57.

**Primary Dependencies**: Existing `@tanstack/react-query` 5.104.0, Zustand, Expo Router, Tamagui, Supabase JS, Zod, and `lottie-react-native`. Reuse the existing web-player dependency and football asset.

**Storage**: Existing application `QueryClient`, public namespace `['match-discovery', date, leagueCode]`; inactive entries collected after 30 minutes. No persistence or second fixture store. Supabase remains the authoritative shared catalog.

**Testing**: Jest/React test renderer with isolated QueryClients, fake clocks and an injected one-check discovery adapter; exercise the same discovery interface as callers. Existing Playwright BDD harness; ARTEMIS-guided Android acceptance before interaction tests are authored.

**Target Platform**: Web and Android, preserving existing native adapter behavior.

**Project Type**: Expo mobile/web application in the existing polyglot repository; this feature changes the client only.

**Performance Goals**: SC-001: usable retained-fresh results within 200 ms in at least 95% of 20 controlled reopen trials/platform. SC-003: usable returned results within 250 ms in at least 95% of mixed-speed trials, with another league pending for at least 15 seconds. Zero equivalent fresh/time-only requests; at most three checks per pending cycle.

**Constraints**: Maximum 16 leagues per transport request; existing selection limit 128 and 4 KiB body limit; existing UTC discovery horizon of today ±7 days. Retention does not grant freshness. No private account/room data, tracking grants, scores, game selections, or provider schedules become owned by discovery cache.

**Scale/Scope**: Four user stories; the shared `MatchList` used by solo setup, host room configuration, and running-game editing. Configured options remain independent from loaded results. The unrelated historical manual-team-list fetch remains functionally unchanged and cannot block fixture controls.

## Design

1. `MatchList` derives selected eligible codes from the configuration it already owns and passes them with the required source date and route activity to `useMatchData`; an empty selection produces no queries. The discovery implementation trims, deduplicates and sorts codes without reading hidden configuration state. Leave the display time window outside query identity.
2. `useQueries` observes the exact current keys. Its query functions each perform one check. The loader coalesces queued keys for the same source date, splits at 16, and resolves each key as soon as that batch returns. Do not await other batches or pending follow-ups before publishing accepted results.
3. Bind the production one-check adapter inside the module's composition: `createMatchDiscoveryApiClient(getFootballMatchService({ followUpPending: false }))`. Add that optional service-factory configuration while preserving omitted/default behavior, including `useLiveScores` identity recovery. The adapter translates the required source date to the existing request shape. Reuse normalization, whole-response validation, error mapping and limits; do not bypass the service with raw fetch or expose the mode flag to picker callers.
4. Retain the existing normalized public fixture projection and group metadata in Query data. `createMatchDiscoveryApiClient` already preserves group source-check timing; raw per-match scheduling/history projections are unnecessary for this cache. Keep that adapter's interface unchanged and preserve the hook's fixture/team projection formats.
5. Apply a deliberate client fixture-reuse policy: a matching complete group with `isStale: false` and a valid source check less than 60 seconds old is reusable. Source check +60 seconds is a fixed deadline, independent of receipt or TanStack `dataUpdatedAt`. Expiry permits another check but does not show an outdated warning for complete server-fresh results. Do not compare per-match timestamps or reconstruct private live-source deadlines. Uncertain timing means retained-but-outdated. This policy is not an assertion about current live scores or save/start eligibility. See [data-model.md](data-model.md).
6. Keep the cycle allowance and retry-not-before instant in shared per-key query data. Let Query deduplicate before enqueueing; reserve each transport check synchronously at dispatch after rechecking active demand. Pending-only `refetchInterval` uses that shared state; `retry: false`, `refetchIntervalInBackground: false`, `refetchOnReconnect: false`. No periodic interval for completed results. A second observer joins, never resets an existing pending cycle.
7. Observe only while the picker route is focused and the application is interactive. The wizard already renders only its current step; use Expo Router focus handling for mounted screens below another route. Reuse `QueryLifecycle` for focus/connectivity. No active observer means no later pending checks. Submitted batches may finish into exact-key cache entries without cancellation; one consumer must not cancel another's work.
8. Explicit Retry joins in-flight work and honors cooldown before starting a new cycle. Exhausted pending cycles require Retry; reopening or foregrounding resumes an unexhausted pending cycle without resetting its allowance. Completed stale entries refresh on mount/reopen, date/league changes or foreground, and never merely because time elapsed.
9. Separate configured chooser options, discovery status, manual-team status and selected game matches. Remove the response-derived league-selection synchronization. Do not disable ready fixture actions because another league or `useTeamData` is loading. Reuse the jumping-football `PlatformAnimation` for initial missing-data feedback; preserve reduced-motion/error fallback and accessible status.
10. Preserve whole-response validation: a transport error or structurally malformed body fails every key in that submitted batch while retaining prior fixtures. After validation succeeds, missing/duplicate/wrong-date group correspondence fails only the affected key; another group's valid result remains usable. Separate submitted batches settle independently. No tolerant parser or weakened validation is introduced.

## Release and Recovery

Deploy only the client after implementation gates pass. Do not apply migrations, deploy Edge Functions, activate acquisition, or modify Cron/freshness/budget settings for this feature. Roll back with the previous client build; session cache disappears on reload/restart and no data repair is required. Existing save/start validation remains authoritative even when retained discovery is old.

## Complexity Tracking

No constitution violations. The batch loader is necessary because TanStack deduplicates queries but does not combine separate league keys into one HTTP request. It stores only transient queued/in-flight work; Query remains the sole retained fixture/cycle store. Client reuse is a source-aged fixture policy, not a copy of server scheduling. Longer backend freshness and any producer-owned exact expiry contract remain separate work.
