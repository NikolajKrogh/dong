# Research: Harden Codebase Foundations

**Feature**: 019-harden-codebase-foundations | **Date**: 2026-07-19

Consolidated findings from the tech-debt audit and three targeted codebase explorations (CI/test infrastructure; ESPN parsing + hook-test patterns; god files + upgrade surface). All NEEDS CLARIFICATION items resolved — user decisions recorded below.

## D1. CI scope and shape

- **Decision**: Two workflow files ship — `client-ci.yml`, `db-ci.yml`. A third, `e2e-ci.yml`, was planned as a fast-follow and attempted, but ultimately abandoned per D11 (unresolved dev-server memory leak, then a dev-vs-production regression) — the Playwright suite stays a local/manual verification tool, not a CI job, in this feature. Mirror `java-ci.yml` conventions: pinned action versions, `persist-credentials: false`, path filtering. Add `"test:ci": "jest --ci"`; keep `"test": "jest --watchAll"` for local dev.
- **Rationale**: `jest --watchAll` hangs CI. Separate files = independent revertibility (user decision). Path filters keep docs-only PRs cheap. `jest.setup.ts` was audited — pure mocks, nothing CI-hostile.
- **Key finding**: the Playwright suite needs **no backend** in CI — `playwright.config.ts` self-boots Expo web on :8093 and `e2e/steps/browser-flow.helpers.ts` mocks every Supabase/command-api call via `page.route()`. The e2e job is only Node + `npx playwright install --with-deps chromium`.
- **DB job**: `npx supabase start` (Docker preinstalled on ubuntu-latest; non-default 553xx ports and 2m health timeout already in `supabase/config.toml`) → `npx supabase test db` (33 pgTAP files) → always-run `supabase stop`. No secrets required.
- **Alternatives considered**: one monolithic workflow (rejected: revert granularity); running e2e against a real local Supabase (rejected: unnecessary — mocks already in place).

## D2. Spring Boot 3.3.5 → 3.5.x

- **Decision**: Bump parent to latest 3.5.x; co-bump `springdoc` 2.6.0 → 2.8.x and `logstash-logback-encoder` 7.4 → 8.x; remove the `maven-compiler-plugin` 3.10.1 pin (incl. `fork`/`executable=javac` override) and let the Boot parent manage it. Leave jjwt 0.12.6 and caffeine 3.1.8.
- **Rationale**: 3.3.x OSS support ended mid-2025 — the JWT-validating service must stay patchable. springdoc 2.6 targets Framework 6.1 (Boot 3.3) and is the highest-risk pin; Boot 3.5 ships Logback 1.5 which predates logstash-encoder 7.4. Code audit found no blockers: security config is already lambda-DSL `SecurityFilterChain` (no `WebSecurityConfigurerAdapter`), HTTP via `RestClient`, jjwt on the modern 0.12 API.
- **Alternatives considered**: stop at 3.4.x (rejected: shorter support runway for the same effort).

## D4. axios / node-fetch removal

- **Rationale**: axios is used in exactly one file (repo-wide grep), no interceptors/instances; node-fetch has zero usages. The fetch version must replicate axios's reject-on-non-2xx and JSON parsing to keep error states identical.

## D10. Trunk branch correction (supersedes original D9 assumption)

- **Decision**: Every phase branches from `origin/multiplayer`, not `origin/master`.
- **Rationale**: empirically verified while attempting to cut the Phase 1 branch: `origin/master` (confirmed as the repo's default HEAD branch) contains no `supabase/` or `command-api/` directory at all — `git ls-tree origin/master` shows neither, and its `package.json` lacks `db:*`/`test:e2e` scripts. `git log origin/master..origin/multiplayer` shows 19 unmerged commits spanning platform abstractions, the Supabase schema/RLS, the Java command-api bootstrap, the ESPN proxy, and host/room features through PR #167. `origin/multiplayer` is where all real feature work has actually landed; `origin/master` is not merely stale, it predates two of the three subsystems this feature exists to remediate. The original plan's "local master is stale" note undersold this — it read as ordinary lag, not a missing-subsystem gap.
- **Impact**: FR-012 and every phase's branch-cut instruction (plan.md, tasks.md, quickstart.md) were corrected from `origin/master` to `origin/multiplayer`. No other phase content changes — the file paths, seams, and task breakdown were derived from the actual working tree (which already reflected `multiplayer`), not from `origin/master`, so they remain valid.
- **Follow-up (out of scope for this feature)**: whether/when `master` should be fast-forwarded or `multiplayer` merged into it is a repository-management decision for the user, not something this feature's phases should attempt.

## D11. e2e-ci: dev-server crash under load, and the nightly-cadence redesign

- **Finding**: Phase 2's `e2e-ci.yml`, once actually run on GitHub Actions (PR #170), failed with 59/96 tests failing on `Error: page.goto: net::ERR_CONNECTION_REFUSED at http://localhost:8093/` — the self-booted Expo dev server (dev-mode, SSR-per-request) stopped responding entirely partway through each ~17.5min run. Distinct from a milder local-sandbox symptom seen earlier (30s per-test `page.waitForFunction` timeouts, 82/14 pass/fail) — the GH Actions failure is a genuine server crash, not just slowness. Both `chromium-phone` and `chromium-desktop` Playwright projects share one `webServer` instance; default worker concurrency across both was apparently enough load to kill it.
- **Fix attempt 1 (wrong hypothesis)**: `playwright.config.ts` set `workers: process.env.CI ? 1 : undefined` to test whether concurrent load across both Playwright projects was killing the shared server. Re-verified via manual dispatch: **worse**, not better — 71/96 failed (vs. 59/96). Serialization increased total wall-clock time without preventing the crash, which itself is evidence concurrency wasn't the driver.
- **Fix attempt 2 (real root cause, still unresolved)**: pulled the actual crash from the job log instead of just the downstream `ERR_CONNECTION_REFUSED` symptom: `[WebServer] FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`, at ~5 minutes of server uptime, independent of worker count. The dev-mode server (SSR-per-request, no production build) has a genuine, apparently unbounded memory leak. Reverted `workers` to default; set `NODE_OPTIONS=--max-old-space-size=6144` in `webServer.env`. Re-verified: GC log confirmed the limit took effect (heap correctly reached ~6.1–6.2GB before crashing) — it delayed the crash proportionally (~5min → ~6.1min) rather than preventing it. The growth rate is roughly linear at ~17MB/sec; extrapolated across a full ~17min run, surviving would need ~17GB of heap — more than a GitHub-hosted runner's total RAM. Raising the limit further is not a viable fix.
- **Fix attempt 3 (user-directed: static export, introduces a different regression)**: replaced the dev server with `npx expo export -p web && npx serve -s dist -p <port>` (static production build — no per-request compilation, so nothing to leak). Locally confirmed route resolution works, including the dynamic `/lobby/[sessionId]` route via `serve -s`'s SPA fallback, and that `EXPO_PUBLIC_*` env vars bake in correctly at export time in a clean environment (no `.env.local` to shadow them, which is the case in CI though not in this dev sandbox). **But a full local e2e run against the static build failed worse than the dev-server baseline: 42/96 failed (vs. 14/96 originally)**, with failures like `getByTestId('home-create-room-button')` never becoming visible within 90s and `LegacyHistoryImportButton` staying `aria-disabled="true"` indefinitely — genuine functional/timing differences between dev-mode and production-mode app readiness, not cosmetic ones. A first check for `__DEV__`/`NODE_ENV`-gated code in the relevant hooks/components/app dirs found nothing obviously responsible. Not root-caused further — this was reverted (never committed) rather than pushing a new regression, since chasing it would mean debugging production-vs-dev app behavior, a materially different and larger investigation than "fix the CI job."
- **Net result / final decision**: three attempts, three different findings, no working fix. **User decision: abandon e2e-ci entirely for this feature** — PR #170 closed unmerged, not added to scope. `client-ci`/`db-ci` (Phase 1) are unaffected and remain the only CI this feature ships. The Playwright suite itself is untouched and still runs via `npm run test:e2e` locally/manually — this decision only removes CI automation of it, nothing about the suite or app behavior. Options for whoever revisits this later (out of scope for this feature): (a) properly root-cause the dev-server memory leak (e.g., is a specific Metro/Tamagui/babel cache never evicted per SSR request?), (b) properly root-cause why production-mode readiness differs from dev-mode for the specific broken flows (auth/session state, disabled-button gating) and pick the static-export path back up, or (c) run a much smaller/shorter e2e subset for nightly monitoring instead of the full 96-test suite, sidestepping the long-run memory growth entirely.
- **Design change (superseding the original Phase 2 plan, user-directed)**: even before confirming the fix, a fully serialized 96-test run is 30-40+ minutes — too slow to gate every PR regardless of whether it passes. Restructured `e2e-ci.yml` from `push`/`pull_request` triggers to `schedule` (nightly cron, 03:00 UTC) + `workflow_dispatch`, with a `check-for-changes` job comparing the current commit's SHA against the `head_sha` of the workflow's last completed run — skipping the Playwright job entirely when nothing has landed since (an idle night costs nothing, matching "run nightly if there's been a PR merged").
- **Caveat surfaced, not resolved**: `schedule`-triggered workflows only fire for files that exist on the repository's *configured default branch*. `git remote show origin` confirms that's `master`, which per D10 is the stale branch missing `supabase/`/`command-api/` entirely and 19 commits behind the real trunk `multiplayer`. This means the nightly cron will not actually fire until this workflow (and the code it tests) reach whichever branch GitHub considers default — the same root issue as D10, resurfacing in a new place. `workflow_dispatch` works immediately regardless, as a manual stopgap. Whether/when to fast-forward `master` remains, as in D10, a repository-management decision outside this feature's scope — but this is the second time it has blocked a phase's design, worth the user's attention.
- **Consequence for FR-013**: the original plan ("e2e-ci joins as a required check once stable") no longer applies — a nightly job cannot gate a PR merge by definition. `e2e-ci` is now a regression-monitoring signal, not a merge gate; FR-013 was corrected accordingly.
